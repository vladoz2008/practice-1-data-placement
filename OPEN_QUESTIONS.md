# Артефакт 2. Список спорных решений

Формат: **[сущность]: [вариант A] vs [вариант B]** → аргументы за каждый → принятое решение.
Цель списка — честно зафиксировать, где решение неочевидно, а не «загладить» неуверенность.

---

**1. Логи действий: ClickHouse vs PostgreSQL**

*Аргументы за PostgreSQL:*
- Не плодим ещё одно хранилище: меньше инфраструктуры, меньше людей, которые должны её знать.
- На старте объём небольшой, партиционирования по дням хватило бы на первый год.
- Джойнить события с пользователями можно прямо в базе, без словарей.

*Аргументы за ClickHouse:*
- Поток событий по определению не имеет верхней границы, а PostgreSQL — единственная база,
  которая обязана оставаться быстрой на боевом пути. Растущая на порядки таблица рядом
  с таблицей заказов рано или поздно съест кэш и вытеснит горячие данные.
- Колоночное сжатие даёт 10–20× на однородных данных против строкового хранения.
- Агрегат по 10⁹ строкам в PostgreSQL — минуты и seq scan; в ClickHouse — секунды.
- Удаление истории: `DROP PARTITION` вместо `DELETE` с раздуванием таблицы и VACUUM.

**Решение: ClickHouse.** Это ровно тот антипаттерн, который проверяется контрольным
вопросом «сущность в PostgreSQL, растущая без лимита». Экономия на инфраструктуре здесь
покупается ценой деградации боевой базы через год.

---

**2. Сессии: всё в Redis vs Redis + PostgreSQL для refresh-токенов**

*Аргументы за «всё в Redis»:*
- Одно хранилище — одна модель, проще код и проще эксплуатация.
- TTL встроен, ручной чистки не нужно.
- Максимальная скорость на всех операциях аутентификации.

*Аргументы за гибрид:*
- Redis в конфигурации с AOF `everysec` допускает потерю последней секунды записей.
  Для access-сессии это ничего; для refresh-токена — пользователь разлогинен «навсегда».
- Отзыв доступа (бан, смена пароля, «выйти со всех устройств») должен переживать
  перезапуск и работать наверняка — это требование к долговечности, а не к скорости.
- Refresh-токенов на порядки меньше, чем проверок сессии: нагрузки на PostgreSQL почти нет.

**Решение: гибрид.** Access-сессия — Redis (частая, дешёвая, восстановимая),
refresh-токен — PostgreSQL (редкая, ответственная, обязана быть durable).
Осознанная цена — два места вместо одного и чуть более сложный код обновления токена.

**3. Курсы и уроки: MongoDB vs PostgreSQL JSONB**

*Аргументы за PostgreSQL JSONB:*
- Убирает целое хранилище из стека — самый весомый аргумент.
- Тело курса и метаданные меняются **в одной транзакции**, рассинхрона не бывает в принципе.
- GIN-индексы по JSONB покрывают поиск по полям документа.

*Аргументы за MongoDB:*
- Курс — это дерево «модули → уроки → материалы» с разным набором полей у разных типов
  курсов. Это ровно тот случай, под который проектировалась документная модель.
- Частичные обновления вложенных элементов (`$set` по пути в массиве) — родная операция;
  в JSONB это переписывание всего документа.
- Change streams дают готовый механизм для переиндексации в Elasticsearch.

**Решение: гибрид с явной границей.** PostgreSQL хранит идентичность и права
(`course_id`, автор, статус, цена) — это участвует в JOIN и требует ACID. MongoDB хранит
тело курса. Границу провели по вопросу «участвует ли поле в проверке прав или в JOIN».

**Честно признаём слабое место:** публикация курса затрагивает две базы и потому не
атомарна. Митигируем паттерном outbox — сначала пишем тело в MongoDB, затем в транзакции
PostgreSQL меняем статус и кладём запись в outbox; если второй шаг упал, в MongoDB остаётся
неопубликованная версия, которая никому не видна. **При объёме до ~10 тыс. курсов
PostgreSQL JSONB был бы обоснованным решением, и мы бы его не защищали как ошибку.**

**4. Прогресс: PostgreSQL vs Cassandra / wide-column**

*Аргументы за Cassandra:*
- `PRIMARY KEY (user_id, lesson_id)` — идеальная модель ключей под этот доступ.
- Горизонтальное масштабирование записи, а прогресс — самая быстрорастущая сущность.
- Отметка урока — идемпотентная запись без транзакций, ровно профиль Cassandra.

*Аргументы за PostgreSQL:*
- На прогрессе висит выдача сертификата: «зачёт курса» — это транзакция, и eventual
  consistency здесь даёт выданный по ошибке документ.
- Аналитика по прогрессу (воронка по урокам) требует произвольных запросов, а в Cassandra
  возможны только запросы по ключам — «проектирование ключей есть проектирование запросов».
- На текущем масштабе (десятки тысяч студентов) PostgreSQL c партиционированием справляется
  с многократным запасом. Cassandra — это плата инфраструктурой за нагрузку, которой нет.

**Решение: PostgreSQL + hash-партиционирование по `course_id`.**
Зафиксирован **триггер пересмотра**: > 500 млн строк или p99 записи > 50 мс.
Это единственная сущность в OLTP с неограниченным ростом, и мы это признаём явно.

**5. Поиск: Elasticsearch vs PostgreSQL full-text search**

*Аргументы за PostgreSQL FTS:*
- Компонент уже есть, `tsvector` + GIN работает из коробки и бесплатно.
- Индекс всегда консистентен с данными — он в той же транзакции, никакого лага.
- На нескольких тысячах курсов производительности заведомо хватает.

*Аргументы за Elasticsearch:*
- **Опечатки.** Задание прямо требует «поиск с опечатками»; fuzzy-матчинга в `tsvector` нет,
  а `pg_trgm` решает задачу лишь частично и плохо сочетается с ранжированием.
- **Ранжирование.** `ts_rank` — фиксированная формула. Настраиваемый скоринг (буст по
  популярности курса, свежести, рейтингу автора) — это то, ради чего берут поисковый движок.
- Фасетные фильтры и агрегации для UI выдачи — родная операция.

**Решение: Elasticsearch,** сверх списка из задания и с явным осознанием цены.
Компромисс: пятый компонент в стеке, отставание индекса на секунды, необходимость
переиндексации. **Если бы требования по опечаткам не было — взяли бы PostgreSQL FTS**
и не добавляли компонент ради одной сущности.

**6. Рекомендации: ClickHouse (батч) vs Neo4j (граф)**

*Аргументы за Neo4j:*
- «Похожие пользователи» — это буквально обход графа `user → course → user`, нативная
  операция графовой базы.
- Позволяет живые запросы по связям вместо суточного отставания.
- Легко расширяется новыми типами рёбер (лайкнул, бросил, порекомендовал).

*Аргументы за ClickHouse + Redis:*
- Нужная нам глубина обхода — 2 уровня. Это обычный `GROUP BY` по событиям, которые
  **уже лежат** в ClickHouse; графовая БД потребовала бы отдельного потока загрузки.
- Данные для расчёта — те же события, что и для аналитики. Новое хранилище не появляется.
- На чтении связи уже свёрнуты в топ-20: `ZREVRANGE` из Redis отдаёт список за доли
  миллисекунды, чего обход графа в реальном времени не даст.

**Решение: ClickHouse для расчёта + Redis для витрины.**
Граф взяли бы, если бы понадобились запросы глубиной 3+ уровня или интерактивный обход
связей (антифрод, «путь между пользователями»). Для «похожих курсов» это избыточно.

**7. Транспорт событий: Kafka vs прямая запись в ClickHouse**

*Аргументы за прямую запись:*
- Минус один компонент инфраструктуры.
- Меньше звеньев — меньше мест, где событие может потеряться.

*Аргументы за Kafka:*
- ClickHouse плохо переносит частые мелкие INSERT: ему нужны крупные батчи, а приложение
  генерирует события по одному. Буферизовать надо где-то — либо в Kafka, либо в памяти
  приложения, где события теряются при рестарте.
- Один поток событий питает **три** потребителя: ClickHouse, Elasticsearch (CDC) и будущие
  подписчики. Без Kafka каждый потребитель тянет данные отдельно.
- Пик нагрузки гасится в очереди, а не в базе; недоступность ClickHouse не роняет запись.

**Решение: Kafka,** сверх списка из задания.
**Оговорка:** на MVP это оверинжиниринг. До ~1000 событий/сек хватило бы буфера в приложении
с флашем раз в 10 секунд, и мы бы начали именно с него.

## Сводка: чем мы сознательно пожертвовали

| Решение | Что получили | Чем заплатили |
|---|---|---|
| Разделение курса на PostgreSQL + MongoDB | Гибкость схемы + целостность прав | Публикация не атомарна, нужен outbox |
| Elasticsearch отдельным компонентом | Опечатки и настраиваемое ранжирование | Пятый компонент, лаг индекса, переиндексация |
| Kafka как транспорт | Батчинг, несколько потребителей, устойчивость к пикам | Инфраструктура, избыточная для MVP |
| Лайки в Redis | Нет блокировок на горячих строках | Потеря единиц лайков при падении Redis |
| Прогресс в PostgreSQL | ACID для сертификатов | Самая быстрорастущая таблица в OLTP |
| Рекомендации батчем | Мгновенное чтение, нет нового хранилища | Отставание до суток |
