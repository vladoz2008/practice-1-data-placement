# Артефакт 2. Список спорных решений

Формат: **[сущность]: [вариант A] vs [вариант B]** → аргументы за каждый → принятое решение.
Цель списка — честно зафиксировать, где решение неочевидно, а не «загладить» неуверенность.

---

### 1. Пользователи: кэшировать права в Redis с TTL vs всегда читать из PostgreSQL

- **Аргументы за кэш в Redis:** проверка прав происходит на каждом запросе, читать её каждый раз
  из PostgreSQL — лишняя нагрузка на основную базу; TTL 5 минут держит компромисс между нагрузкой
  и актуальностью.
- **Аргументы за чтение напрямую:** права — критические данные, лаг при отзыве доступа это риск
  безопасности.
- **Решение:** кэшируем с TTL 5 минут + принудительное удаление ключа при смене роли; для критичных
  действий (удаление курса, выплаты) права читаются напрямую из PostgreSQL, минуя кэш.

### 2. Сессии и токены: серверное хранение в Redis vs stateless JWT

- **Аргументы за Redis:** можно мгновенно отозвать сессию (разлогинить пользователя принудительно),
  TTL встроен.
- **Аргументы за JWT:** не нужно отдельное хранилище, меньше инфраструктуры.
- **Решение:** Redis для access-сессий, потому что мгновенный отзыв важнее экономии на инфраструктуре.
  Refresh-токены при этом вынесены в PostgreSQL: они обязаны пережить перезапуск, а Redis с AOF
  `everysec` допускает потерю последней секунды записей.

### 3. Курсы и уроки: единая база (PostgreSQL, JSONB или EAV) vs разделение на PostgreSQL + MongoDB

- **Аргументы за единую базу:** один источник истины, не нужна синхронизация, тело и метаданные
  меняются одной транзакцией.
- **Аргументы за разделение:** метаданные курса нуждаются в целостности и связях (FK), а тело курса
  имеет разную вложенную структуру у разных курсов — в реляционной схеме это выродилось бы в неудобную
  EAV-модель; частичное обновление вложенного элемента в MongoDB родное, в JSONB это переписывание
  всего документа.
- **Решение:** разделили — метаданные в PostgreSQL, контент в MongoDB, синхронизация через transactional
  outbox. Цена решения — дополнительная сложность и неатомарная публикация. Признаём: до примерно
  10 тысяч курсов JSONB был бы обоснованным выбором.

### 4. Прогресс по курсам: только Redis vs только PostgreSQL vs оба

- **Аргументы за только Redis:** максимальная скорость чтения текущего состояния.
- **Аргументы за только PostgreSQL:** надёжное хранение истории и результатов, но медленнее при большом
  числе пользователей.
- **Решение:** PostgreSQL как источник истины (транзакционность нужна для зачёта и сертификата) + Redis
  как write-through кэш текущего состояния + ClickHouse для истории событий. Зафиксирован порог
  пересмотра: **500 млн строк или p99 записи выше 50 мс** — после этого сущность уезжает в wide-column.

### 5. Поиск по курсам: PostgreSQL full-text search vs Elasticsearch

- **Аргументы за PostgreSQL FTS:** не нужна отдельная инфраструктура, встроенные триграммы под опечатки,
  для среднего объёма достаточно.
- **Аргументы за Elasticsearch:** специализированный инвертированный индекс, лучше справляется со сложным
  ранжированием при росте числа курсов; `ts_rank` — фиксированная формула, а нужен настраиваемый буст
  по популярности и свежести.
- **Решение:** Elasticsearch — заложились на рост объёма и необходимость сложного ранжирования.
  Цена: пятый компонент в стеке и лаг индексации в секунды.

### 6. Форум / обсуждения: дерево ответов в PostgreSQL (CTE) vs документ в MongoDB

- **Аргументы за PostgreSQL:** удобно считать лайки и вести модерацию с аудитом и целостностью.
- **Аргументы за MongoDB:** удобно хранить всю ветку обсуждения одним документом при вложенных ответах.
- **Решение:** PostgreSQL — модерация и целостность важнее, но признаём: при большом объёме вложенности
  MongoDB могла бы упростить чтение целой ветки.

### 7. Логи действий: прямая запись в ClickHouse vs буфер (Kafka / Redis Streams) перед ClickHouse

- **Аргументы за прямую запись:** меньше инфраструктуры на старте проекта.
- **Аргументы за буфер:** сглаживает пиковую нагрузку, не теряет события при кратковременной
  недоступности ClickHouse, батчует вставки — а ClickHouse плохо переносит частые мелкие INSERT.
- **Решение:** заложили буфер с самого начала, поток событий изначально может быть неравномерным.
  Оговорка: на MVP до примерно 1000 событий в секунду хватило бы буфера в самом приложении.

### 8. Аналитика и отчёты: витрины в реальном времени vs материализованные представления по расписанию

- **Аргументы за реальное время:** всегда свежие данные.
- **Аргументы за расписание (cron 15 мин):** тяжёлые агрегаты не нагружают систему постоянно,
  а считаются пакетом.
- **Решение:** материализованные представления, cron раз в 15 минут — свежесть T+15 мин признана
  приемлемой ценой за экономию ресурсов.

### 9. Рекомендации курсов: расчёт в ClickHouse vs выделенная графовая БД (Neo4j)

- **Аргументы за ClickHouse:** матрица «пользователь × курс» уже там лежит, не нужна новая система;
  нужная глубина обхода — два уровня, это обычный `GROUP BY`.
- **Аргументы за Neo4j:** для сложных коллаборативных фильтров графовая база или отдельный сервис
  рекомендаций работает нативнее.
- **Решение:** пока ClickHouse (батчевый расчёт раз в сутки + выдача из Redis), с открытым вопросом
  перехода на Neo4j при усложнении алгоритмов или необходимости обхода глубиной 3+ уровня.

## Сводка: чем мы сознательно пожертвовали

| Решение | Что получили | Чем заплатили |
|---|---|---|
| Кэш прав с TTL 5 мин | Разгрузили PostgreSQL на каждом запросе | Лаг до 5 минут при отзыве доступа |
| Разделение курса на PostgreSQL + MongoDB | Гибкость схемы + целостность прав | Публикация не атомарна, нужен outbox |
| Elasticsearch отдельным компонентом | Опечатки и настраиваемое ранжирование | Пятый компонент, лаг индекса, переиндексация |
| Буфер событий (Kafka) | Батчинг, устойчивость к пикам | Инфраструктура, избыточная для MVP |
| Лайки в Redis | Нет блокировок на горячих строках | Потеря единиц лайков при падении Redis |
| Прогресс в PostgreSQL | ACID для сертификатов | Самая быстрорастущая таблица в OLTP |
| Витрины по расписанию | Агрегаты не нагружают систему постоянно | Свежесть T+15 мин |
| Рекомендации батчем | Мгновенное чтение, нет нового хранилища | Отставание до суток |
