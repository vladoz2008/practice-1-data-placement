# Этап 4. Синхронизация и потоки данных

Шаблон: `[сущность] → [хранилище-источник] → [какой механизм] → [производное хранилище]`

| Сущность | Источник | Механизм | Производное хранилище |
|---|---|---|---|
| [Пользователи] | **PostgreSQL** | cache-aside + DEL при UPDATE | [Redis: `profile` / `perm`] |
| [Пользователи] | **PostgreSQL** | CDC (Debezium) / ночной ETL | [ClickHouse: `dim_users`] |
| [Сессии и токены] | **Redis** | событие login / logout | [ClickHouse: `events`] |
| [Курсы: метаданные] | **PostgreSQL** | transactional outbox → брокер | [Elasticsearch, Redis, ClickHouse: `dim_courses`] |
| [Курсы: контент] | **MongoDB** | обработчик `course.published` | [Elasticsearch (денорм. документ), Redis] |
| [Прогресс] | **PostgreSQL** | write-through при отметке урока | [Redis: `progress`] |
| [Прогресс] | **PostgreSQL** | инкрементальный ETL по `updated_at` | [ClickHouse: `fact_progress`] |
| [Форум: лайки] | **Redis** | flush раз в минуту (INCR → SUM) | [PostgreSQL: `posts.likes_count`] |
| [Логи действий] | **приложение** | Kafka / Redis Streams, батч 10 000 | [ClickHouse: `events`] |
| [Аналитика] | **ClickHouse** | materialized views, cron 15 мин | [ClickHouse: `mart_*`] |
| [Рекомендации] | **ClickHouse** | батч item-item, cron раз в сутки | [Redis: `rec:user:*`] |

## Что происходит при обновлении

**Автор публикует курс.** В PostgreSQL одной транзакцией меняется статус курса и пишется запись
в таблицу outbox — паттерн transactional outbox: событие не может потеряться, если транзакция прошла,
и не появится, если она откатилась. Отдельный воркер читает outbox и публикует `course.published`.
Подписчики: индексатор собирает денормализованный документ из PostgreSQL и MongoDB и кладёт
в Elasticsearch; кэш-инвалидатор удаляет `course:pub:{id}`; ETL обновляет справочник в ClickHouse.
Лаг индекса — секунды, это допустимо.

**Пользователь отмечает урок пройденным.** Запись в PostgreSQL, в той же транзакции пересчитывается
процент завершения. После коммита обновляется `progress:{user}:{course}` в Redis (write-through;
при ошибке — просто DEL, пересоберётся при следующем чтении). Параллельно приложение шлёт событие
`lesson.completed` в буфер → ClickHouse. Прогресс и событие живут отдельно: первый — состояние,
второе — факт.

**Пользователь меняет профиль.** UPDATE в PostgreSQL → DEL ключа в Redis (именно инвалидация,
а не перезапись: так проще и нет гонок, когда две параллельные записи оставляют в кэше проигравшую
версию) → CDC доносит изменение в справочник ClickHouse. TTL остаётся страховкой на случай
потерянной инвалидации.

**Курс удаляют.** Мягкое удаление в PostgreSQL (`deleted_at`), уход из Elasticsearch и кэша.
В ClickHouse события о курсе остаются: история не переписывается задним числом, иначе ломается
вся аналитика за прошлые периоды.

## Деградация: что ломается, если хранилище недоступно

| Упало | Последствие |
|---|---|
| Redis | Все пользователи разлогинены, нагрузка на PostgreSQL растёт кратно. **Критично** |
| Elasticsearch | Поиск не работает, каталог и навигация по категориям живут. Частичная деградация |
| ClickHouse | Отчёты и рекомендации недоступны, обучение идёт как обычно. Не критично |
| MongoDB | Карточки курсов видны, содержимое уроков не открывается. **Критично** |
| PostgreSQL | Платформа не работает. **Критично** |
