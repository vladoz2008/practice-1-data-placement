# Артефакт 3. Git Issue

Оформлен в репозитории: [Issue #1](../../issues/1)

**Title:** Storage architecture v1 — Data Placement Map

---

## Решения

- **Пользователи:** PostgreSQL (источник истины) + Redis (кэш профиля, TTL 15 мин)
- **Сессии и токены:** Redis (access-сессии, TTL) + PostgreSQL (refresh-токены, отзыв доступа)
- **Курсы и уроки:** PostgreSQL (метаданные, права) + MongoDB (тело курса)
- **Прогресс по курсам:** PostgreSQL (hash-партиционирование по `course_id`) + Redis (кэш позиции)
- **Поиск по курсам:** Elasticsearch (производный индекс)
- **Форум / обсуждения:** PostgreSQL (рекурсивные CTE) + Redis (счётчики лайков)
- **Логи действий:** Kafka → ClickHouse (партиции по дням, TTL 12 мес)
- **Аналитика и отчёты:** ClickHouse (материализованные представления, cron 15 мин)
- **Рекомендации курсов:** ClickHouse (ночной батч) → Redis ZSET (топ-20)

## Открытые вопросы

1. Публикация курса затрагивает PostgreSQL и MongoDB и не атомарна. Достаточно ли outbox или свернуть
   тело курса в JSONB? Порог — около 10 тыс. курсов.
2. Прогресс — единственная сущность в OLTP с неограниченным ростом. Порог выноса в wide-column:
   500 млн строк или p99 записи выше 50 мс.
3. Оправдан ли Elasticsearch ради одной сущности? Входит ли поиск с опечатками в MVP или переносится на v2.
4. Буфер событий: вводим Kafka сразу или по достижении примерно 1000 событий в секунду.
5. Допустимое отставание витрин: 5 минут для оперативных, сутки для тяжёлых — нужно подтверждение
   заказчика аналитики.
6. Кэш прав с TTL 5 минут даёт лаг при отзыве доступа — согласовать допустимость с безопасностью.
7. Потеря лайков при падении Redis — требует явного согласования с продуктом.
