# Этап 1. Постановка задачи — распределение сущностей по хранилищам

Доступные хранилища из задания: PostgreSQL, Redis, MongoDB, ClickHouse.
Сверх списка предложены **Elasticsearch** (поиск с опечатками и настраиваемым ранжированием)
и брокер событий **Kafka** (буферизация потока и CDC) — задание допускает аргументированное расширение.

| № | Сущность / поток | Хранилище | Характер нагрузки | Обоснование | Операции | Спорные моменты |
|---|---|---|---|---|---|---|
| 1 | **Пользователи** | PostgreSQL + Redis (кэш профиля) | Средняя частота записи, очень частое чтение, малый объём | Нужны связи с ролями и целостность: пользователь без роли — сломанное состояние. Регистрация проходит одной транзакцией, JOIN к ролям — родная операция реляционной БД | Регистрация, вход, редактирование профиля, проверка прав | Профиль можно было положить в MongoDB, но тогда теряется целостность и усложняются связи с ролями |
| 2 | **Сессии и токены** | Redis + PostgreSQL (refresh-токены) | Экстремально частый доступ по ключу, короткая жизнь записи | TTL встроен в Redis — чистить вручную не надо, in-memory даёт < 1 мс на пути каждого запроса. Refresh-токены вынесены в PostgreSQL: их нужно уметь отзывать и переживать перезапуск | Создание, проверка, истечение по TTL | Можно было держать всё в Redis или уйти в stateless JWT, но тогда мгновенный отзыв доступа теряется |
| 3 | **Курсы и уроки** | PostgreSQL (метаданные) + MongoDB (тело курса) | Редкая запись автором, очень частое чтение, вложенная структура | Метаданные (автор, статус, цена) участвуют в правах и JOIN — им нужен ACID. Тело курса — дерево с разным набором полей у разных типов курсов, в реляционной схеме это выродилось бы в EAV | Создание автором, редактирование, публикация | Можно было обойтись PostgreSQL JSONB и не заводить вторую базу, но частичные правки вложенных элементов дороже |
| 4 | **Прогресс по курсам** | PostgreSQL (партиционирование) + Redis (кэш позиции) | Частая запись, ещё более частое чтение, объём растёт как users × lessons | Результат теста влияет на зачёт курса и выдачу сертификата — нужна транзакционность. Схема жёсткая, объём спасает hash-партиционирование по `course_id` | Отметка пройденных уроков, результаты тестов | Только Redis потерял бы историю, только PostgreSQL медленнее при большом числе пользователей |
| 5 | **Поиск по курсам** | Elasticsearch (производный индекс) | Только чтение, переиндексация по событию | Опечатки, стемминг и настраиваемое ранжирование — это инвертированный индекс с анализаторами. Индекс полностью производный: его потеря лечится переиндексацией, а не восстановлением | Полнотекстовый поиск по названию и описанию, фильтры, ранжирование | Для среднего объёма хватило бы PostgreSQL FTS с триграммами; Elasticsearch — задел на рост и сложный скоринг |
| 6 | **Форум / обсуждения** | PostgreSQL + Redis (счётчики лайков) | Чтение > запись, древовидная структура, умеренный объём | Дерево ответов ложится на `parent_id` и рекурсивные CTE, модерация требует целостности и аудита. Лайки — частая мелкая запись без требования точности, поэтому `INCR` в Redis | Создание тем, ответы, лайки | MongoDB удобнее, если хранить всю ветку одним документом; выбрали целостность и модерацию |
| 7 | **Логи действий** | Kafka (буфер) → ClickHouse | Огромный объём записи, редкие пакетные чтения, append-only | Событие неизменяемо — ни UPDATE, ни транзакций не нужно. Колоночное сжатие даёт 10–20×, партиционирование по дням превращает удаление истории в `DROP PARTITION` вместо `DELETE` | Поток событий: клики, просмотры уроков, старт и завершение тестов | Прямая запись в ClickHouse проще, но он плохо переносит частые мелкие INSERT и пиковую нагрузку |
| 8 | **Аналитика и отчёты** | ClickHouse (материализованные витрины) | Тяжёлые агрегаты по истории, редкие ресурсоёмкие запросы | Агрегат по миллиардам строк — профиль OLAP. В OLTP-базе такой запрос читает всю таблицу и конкурирует за ресурсы с боевой нагрузкой: отчёт кладёт продакшн | «Сколько прошли курс за месяц», «средний процент завершения», «воронка по урокам» | Витрины в реальном времени всегда свежие, но дороже; выбран пересчёт по расписанию |
| 9 | **Рекомендации курсов** | ClickHouse (расчёт) → Redis ZSET (выдача) | Редкий батчевый пересчёт, очень частое чтение при рендере | Матрица «пользователь × курс» уже лежит в ClickHouse — co-occurrence считается обычным `GROUP BY`. Результат сворачивается в короткий список id и отдаётся из Redis Sorted Set за доли миллисекунды | «Похожие курсы», «популярное у похожих пользователей» | Для сложных коллаборативных фильтров нативнее графовая БД (Neo4j) или отдельный сервис рекомендаций |
